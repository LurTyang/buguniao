# 01 · 产品定义与范围

## 1. 产品定位

**不咕鸟**是一款面向**长篇小说作者**的双端写作工作台。

它解决的不是「怎么打字」，而是长篇写作特有的三个痛点：

| 痛点 | 不咕鸟的答案 |
|---|---|
| 写到八十万字，忘了第十二章埋的那块玉佩 | 伏笔追踪 + 全文检索 + AI 资料员 |
| 灵感总在通勤路上冒出来，回家就忘了 | 手机端灵感碎片，一键收进大纲 |
| 写不下去，开始咕 | 码字统计、热力图、番茄钟、手机端提醒 |

## 2. 目标用户

**一期：作者本人。**

不做新手引导、不做账号系统、不做多用户、不做云端服务。
但架构上留好扩展余地（见 [02-技术架构](02-技术架构.md) 第 6 节），以后想开放不用重写。

## 3. 使用场景

| 场景 | 设备 | 典型动作 |
|---|---|---|
| **认真码字** | Windows 桌面 | 开番茄钟，写正文，随手拖两张便利贴出来对照设定，写完看今天字数 |
| **随手记灵感** | Android 手机 | 想到一个梗，打开 App 记一条；查一下某个角色的设定；被提醒「今天还没写」 |
| **整理构思** | Windows 桌面 | 看大纲、拉伏笔连线、问 AI「这个角色上次出场是哪章」 |

**关键判断：两端不对等。** 手机端是「写作的附属品」，不是「小一号的桌面端」。
这个判断是整个同步方案能成立的前提。

## 4. 四条设计原则（铁律）

### 原则一：文件即真相

正文、大纲、设定集全部是坚果云同步文件夹里的 `.md` 纯文本文件。
用记事本、Typora、Obsidian、VSCode 都能直接打开编辑。

数据库里的一切（检索索引、关联图、卡片缓存）都是**派生物**，可以随时从文件重建。

> **为什么：** 写作软件的最大风险是「软件死了，稿子跟着陪葬」。纯文本是唯一能对抗这个风险的存储形式。

### 原则二：手机只增不改

手机端**只能新建**灵感碎片（每条一个独立文件），**只读**查看正文与设定。
它永远不会修改一个已存在的文件。

> **为什么：** 双向同步的地狱是冲突合并。而「只新增文件、不修改文件」这个约束，
> 让冲突在**物理上不可能发生**——两台设备永远不会写同一个文件。
> 这比做一套复杂的冲突检测与三方合并界面便宜一百倍，而且更可靠。

### 原则三：索引可重建

索引库（SQLite）**不放在同步文件夹里**，存在应用数据目录，每台设备一份，各管各的。

索引库损坏、版本升级、换电脑 → 重新扫描一遍作品文件夹即可，几十秒的事，不丢任何数据。

> **为什么：** 数据库文件是二进制大文件，一旦丢进网盘同步，两端同时写就会产生
> 无法合并的冲突副本，且冲突后无法人工修复。必须在架构上把它排除在同步之外。

### 原则四：AI 永不自动运行

所有 AI 能力（续写、润色、抓虫、资料查询、联网搜索）**必须由作者手动点击触发**。

- 不后台扫描、不自动分析、不主动弹提示
- AI 的输出永远进入**独立面板**，作者手动决定是否采纳
- AI 绝不直接修改正文文件

> **为什么：** 一是费用可控（API 按 token 计费，后台偷跑会烧钱），
> 二是创作主权 —— 这是作者的书。

## 5. 功能范围

### 一期（首个可用版本）

| 模块 | 具体内容 |
|---|---|
| **书架** | 多作品管理，封面，按「连载中 / 完结 / 坑啦！哈哈」分类 |
| **编辑器** | Markdown 编辑器，实时预览样式，大文档流畅（百万字级） |
| **目录/大纲** | 卷-章-节 树形结构，拖拽排序，章节字数显示 |
| **设定集 & 便利贴** | 自由 Markdown 文档 + `@` 语法自动抽卡，卡片可拖出悬浮 |
| **伏笔追踪** | 正文选中标「埋/收」，独立清单先记后写，未回收清单，到期提醒 |
| **全文检索** | 中文全文检索，跨正文/大纲/设定集/灵感碎片 |
| **版本历史** | 每次保存存一版，可回溯任意时刻，可手动打命名标记，容量上限预警 |
| **统计与番茄钟** | 字数统计、日/周/月曲线、年度热力图、番茄钟 |
| **AI 助手** | 填 API Key，资料员问答、联网搜索（可关）、续写、润色、抓虫 |
| **同步** | 桌面端走坚果云同步文件夹；Android 端走 WebDAV 直连 |
| **导入导出** | 导入大块 txt 自动分章；导出完整 txt / Word |
| **移动端** | 灵感碎片记录、只读查看、番茄钟提醒推送 |

### 二期

| 模块 | 说明 |
|---|---|
| **按章分文件导出** | 每章一个 txt，方便往起点/飞卢批量上传。（若一期工作量允许则提前做） |
| **剧本模式** | 角色名/台词/动作自动对齐排版，按角色统计台词量 |
| **分支剧情可视化** | 游戏文案的选项分支节点图 |
| **从其他软件导入** | 青茉、码字精灵、Scrivener 等的项目迁移 |
| **大纲伏笔连线图** | 在大纲视图上画伏笔的埋→收连线（带开关，默认关） |

> 大纲伏笔连线图放二期的原因：一期先把伏笔的**数据**做对，
> 有了数据以后画图只是渲染问题。而且一期可以先用「未回收清单」这个更实用的形式代替。

### 明确不做

| 不做的东西 | 理由 |
|---|---|
| 账号系统 / 云端服务器 | 自用，且违反「文件即真相」 |
| 协同编辑 | 单人写作，且极大增加复杂度 |
| 手机端编辑正文 | 违反原则二，会引入冲突合并地狱 |
| iOS 版 | 自用需开发者账号或每 7 天重签，成本不划算 |
| 富文本 / 所见即所得的双向转换 | Markdown 往返会丢信息，违反原则一 |
| AI 自动改稿 / 自动分析 | 违反原则四 |

## 6. 名字与调性

**不咕鸟** —— 不鸽、不断更。

产品调性上允许一点幽默感，比如书架分类里的「坑啦！哈哈」就保留原样，不要改成「已搁置」这种正经词。
这是给作者自己看的软件，自嘲比说教好用。

**提醒策略：**
- **电脑端不打扰。** 写作时任何弹窗都是干扰，桌面端只做安静的统计展示。
- **手机端可以推送。** 因为手机是「不在写作状态」时的设备，提醒才有意义。
