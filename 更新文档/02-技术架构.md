# 02 · 技术架构

## 1. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| **语言** | TypeScript | 一套语言两端复用；生态与 AI 辅助开发的资料最充足 |
| **UI 框架** | React 18 | 生态最大，编辑器与拖拽库的支持最好 |
| **桌面壳** | Electron | Node.js 全套 API（文件 IO、SQLite、加密存储）开箱即用；调试与打包成熟 |
| **移动壳** | Capacitor + Android | 复用同一套 React 代码打 APK；只需少量原生插件 |
| **编辑器内核** | CodeMirror 6 | 百万字级性能过关；原生 Markdown 源码编辑 + 实时装饰（Obsidian 同款） |
| **索引库** | **Node 内置 `node:sqlite`** + FTS5 | 见下方说明：不引入原生模块 |
| **状态管理** | Zustand | 轻量，够用，不引入 Redux 的样板代码 |
| **构建** | Vite + pnpm workspace | 快，且天然支持 monorepo |
| **AI SDK** | `@anthropic-ai/sdk` | 官方 SDK；详见 [05-功能模块详述](05-功能模块详述.md) 第 9 节 |

### 为什么不选 Tauri

Tauri 体积更小、内存更低，但：
- 后端是 Rust，出问题时的调试成本对本项目不划算
- 需要的文件 IO / SQLite / 安全存储在 Electron 里是现成的
- 写作软件不是性能敏感应用，Electron 的开销可以接受

**结论：优先开发效率，选 Electron。** 若后期体积成为痛点，UI 层代码可直接迁移到 Tauri（React 部分不用改）。

### 为什么用 node:sqlite 而不是 better-sqlite3

`better-sqlite3` 是 Node 生态里最常用的 SQLite 绑定，但它是**原生模块** ——
在 Electron 里要按 Electron 的 ABI 重新编译，是这类项目最常见的翻车点
（换 Electron 版本、换机器、打包时都可能炸）。

2026-08-25 实测：**Electron 43 内置的 Node 24.18 自带 `node:sqlite`，
且 FTS5 的 `trigram` 分词器可用**（建表插入中文后搜子串成功）。
因此完全不需要原生模块。

验证方式（会真的启动 Electron 跑一遍）：

```bash
cd 不咕鸟/app/packages/desktop && pnpm smoke
```

结果里的 `env.nodeSqlite` 与 `env.fts5Trigram` 就是这两项。

### 索引库放一个还是每本一个

规范初版写的是每本书一个 `{bookId}.db`，实现时改成**整个库一个 `index.db`**，
用 `book` 列区分。理由：
- 简单，不用管理一堆文件句柄
- 顺带支持跨作品检索（「我在哪本书里写过这个梗」），这个能力挺有用
- 索引是派生物，一个文件坏了重扫就行，不存在「一损俱损」的风险

### 为什么不用 Git 做版本历史

Git 是最诱人的选择（免费拿到完整版本历史），但**它和网盘同步是天敌**：
`.git` 目录里的索引文件、packfile 是二进制的，两台设备同时提交必然产生冲突副本，
而 Git 仓库一旦被网盘搞坏，普通用户无法修复。

**结论：自建纯文本增量历史**，见 [03-数据格式规范](03-数据格式规范.md) 第 6 节。

## 2. 三层架构

```
┌─────────────────────────────────────────────────────────┐
│  应用层  (React UI)                                      │
│  书架 / 编辑器 / 大纲 / 便利贴 / 伏笔 / 统计 / AI面板      │
└────────────────────────┬────────────────────────────────┘
                         │  只读索引 · 写文件
┌────────────────────────▼────────────────────────────────┐
│  索引层  (SQLite，本机，不同步)                            │
│  全文检索(FTS5) · 便利贴缓存 · 伏笔关系 · 章节元数据        │
│  ★ 可随时从文件层重建，损坏不影响任何数据                   │
└────────────────────────┬────────────────────────────────┘
                         │  扫描 · 监听变化
┌────────────────────────▼────────────────────────────────┐
│  文件层  (坚果云同步文件夹，唯一真相源)                     │
│  正文.md · 大纲.md · 设定集.md · 灵感碎片.md               │
│  .bugu/ 版本历史 · 统计 · 伏笔元数据 · 便利贴布局           │
└─────────────────────────────────────────────────────────┘
```

**数据流铁则：**
- 任何修改**只能写文件层**，然后由文件监听触发索引层更新
- 索引层**只读不写**文件层
- UI 从索引层查询（快），从文件层读取正文（准）

## 3. 同步方案

### 3.1 桌面端（Windows）

不实现任何同步逻辑。作品文件夹放在**坚果云本地同步文件夹**内，
由坚果云客户端负责上传下载。软件只是普通的本地文件读写。

```
C:\Users\你\坚果云\不咕鸟\
├── 第九神座\          ← 一个作品一个文件夹
├── 何忆卫\
└── _灵感箱\           ← 未归属到具体作品的灵感碎片
```

### 3.2 移动端（Android）

**不能**依赖坚果云 App 同步文件夹——安卓上的网盘客户端不做本地文件夹双向同步。

改为：**App 内直接用 WebDAV 协议连坚果云**。

- 坚果云 WebDAV 地址：`https://dav.jianguoyun.com/dav/`
- 认证：账号 + **应用密码**（在坚果云网页版「安全选项」生成，不是登录密码）
- 应用密码用 Android Keystore 加密存储

### 3.3 流量控制（重要）

坚果云免费版限额：**上传 1 GB/月，下载 3 GB/月**。

纯文字本身极小，但**如果手机端每次打开都全量拉取整本书，流量会爆**。
必须做增量同步：

1. `PROPFIND` 取文件列表 + `getlastmodified` + `getetag`
2. 与本地缓存的 etag 对比，**只下载变化过的文件**
3. 正文文件**按需下载**（点开某章才拉那一章），不预加载全书
4. 设定集文件较小，可以在 WiFi 下预拉全量以支持离线查阅
5. 设置里提供「仅 WiFi 同步」开关和本月流量估算显示

### 3.4 冲突安全网

设计上不该产生冲突，但仍需兜底：坚果云在检测到冲突时会生成
`文件名 (冲突文件 2026-08-25 14-30 设备名).md` 这样的副本。

软件启动扫描时若发现这类文件：
- 不自动处理、不自动删除
- 在书架和编辑器顶部显示黄色横幅提示
- 提供并排对比视图，由作者手动决定保留哪份

### 3.5 备选存储后端

存储访问必须抽象成一个接口，便于将来更换：

```typescript
interface StorageBackend {
  list(path: string): Promise<FileEntry[]>
  read(path: string): Promise<string>
  write(path: string, content: string): Promise<void>
  stat(path: string): Promise<{ mtime: number; etag?: string; size: number }>
  delete(path: string): Promise<void>
}
```

一期实现两个：`LocalFsBackend`（桌面）、`WebDavBackend`（移动）。
将来若换 Syncthing / OneDrive / 自建服务器，只需新增一个实现。

## 4. 中文全文检索方案

SQLite FTS5 默认的分词器**不支持中文**（会把整段中文当成一个词）。

**方案：使用 FTS5 的 `trigram` 分词器。**

```sql
CREATE VIRTUAL TABLE doc_fts USING fts5(
  doc_id UNINDEXED,
  title,
  body,
  tokenize = 'trigram'
);
```

- `trigram` 把文本切成连续三字片段，对中文有效，**且是 SQLite 内置的，无需编译第三方扩展**
- 支持任意子串匹配（`LIKE '%玉佩%'` 的效果但走索引）
- 代价：索引体积约为原文的 3~4 倍。百万字小说约 12 MB，完全可接受

**限制与对策：** trigram 要求查询串至少 3 个字符。
搜 1~2 个字时降级为 `LIKE` 全表扫描（对单本书的数据量而言仍是毫秒级）。

## 5. 仓库结构（monorepo）

```
不咕鸟/
├── 更新文档/                    ← 本文档目录
├── packages/
│   ├── core/                   ← 【两端共享】纯逻辑，零平台依赖
│   │   ├── markdown/           ← Markdown 解析、章节切分
│   │   ├── sticky/             ← 便利贴 @ 语法解析器
│   │   ├── foreshadow/         ← 伏笔标记解析
│   │   ├── history/            ← 版本历史 diff/patch
│   │   ├── storage/            ← StorageBackend 接口定义
│   │   └── types/              ← 全项目共享类型
│   ├── ui/                     ← 【两端共享】React 组件
│   ├── desktop/                ← Electron 主进程 + 桌面专属界面
│   └── mobile/                 ← Capacitor 配置 + 移动专属界面
├── package.json
└── pnpm-workspace.yaml
```

**关键约束：`packages/core` 里不允许出现任何 `fs`、`window`、Electron、Capacitor 的引用。**
它必须是纯函数库，这样两端才能真正复用，而且好写单元测试。

## 6. 为「以后开放给别人用」预留的接口

虽然一期是自用，但下面几件事现在做只花几分钟，以后补要重构：

| 预留点 | 现在怎么做 |
|---|---|
| 多用户 | 所有路径都从「作品根目录」变量拼接，不硬编码绝对路径 |
| 多存储后端 | 已抽象 `StorageBackend`（见 3.5） |
| 多文档类型 | 文档 front-matter 里带 `type` 字段（`chapter` / `outline` / `setting` / `idea` / `script`），解析器按 type 分派 |
| 多 AI 供应商 | AI 调用抽象成 `AiProvider` 接口，一期只实现 Anthropic |
| 数据格式演进 | 每个 `.bugu/` 下的数据文件带 `schemaVersion` 字段 |

## 7. 安全与隐私

| 数据 | 存储位置 | 保护方式 |
|---|---|---|
| AI API Key | 桌面：`%APPDATA%/bugu/secrets.enc`<br>移动：Android Keystore | Electron `safeStorage` 加密 / Keystore |
| 坚果云应用密码 | 同上 | 同上 |
| 索引库 | `%APPDATA%/bugu/index/{bookId}.db` | 不加密（可从文件重建，无独有价值） |
| 正文 | 坚果云同步文件夹 | 明文（这是「文件即真相」的必然代价） |

**铁则：任何密钥类数据永远不得写入同步文件夹。**

**AI 数据外发提示：** 使用 AI 功能时会把相关正文片段发送到 API 服务商。
设置页需明确告知这一点，并提供「AI 功能总开关」（默认关闭）。
